## 0. AI 개발 공통 원칙

AI는 모든 작업을 시작하기 전에 아래 항목을 먼저 확인해야 한다.

- [ ] 현재 작업이 요구사항 문서의 어떤 항목을 구현하는지 명확히 설명한다.
- [ ] 핵심 용어는 반드시 `Lot`, `Strategy`, `StrategyRule`, `PositionRule`, `SellHistory`를 기준으로 사용한다.
- [ ] 같은 종목의 추가 매수는 기존 Lot과 합치지 않고 별도 Lot으로 저장하는지 확인한다.
- [ ] 평균단가 중심 설계가 아니라 Lot별 독립 수익률 계산 구조인지 확인한다.
- [ ] Strategy 변경이 기존 Lot의 PositionRule에 영향을 주지 않는지 확인한다.
- [ ] 한국/미국 주식과 통화, 환율 처리를 고려했는지 확인한다.
- [ ] Google 소셜 로그인 기반 사용자 분리 저장을 고려했는지 확인한다.
- [ ] Linux 서버 배포 가능성을 해치지 않는 방식인지 확인한다.
- [ ] 임시 구현, 하드코딩, 테스트용 우회 로직이 남아 있지 않은지 확인한다.
- [ ] 구현 후에는 관련 테스트 또는 검증 방법을 반드시 제시한다.

## 1. 요구사항 기준선

AI는 개발 중 아래 요구사항을 임의로 변경하면 안 된다. 변경이 필요하면 먼저 변경 사유와 영향을 설명해야 한다.

### 1-1. 확정된 기준

- [ ] 기준 문서는 Claude 설계문서를 수정한 통합 요구사항 문서이다.
- [ ] 핵심 관리 단위는 `Lot(매수 묶음)`이다.
- [ ] 로그인은 Google 소셜 로그인을 기준으로 한다.
- [ ] 배포 환경은 Linux 서버를 기준으로 한다.
- [ ] 환율 API는 `ExchangeRate-API`를 기준으로 한다.
- [ ] DB 상세 설계는 이 체크리스트 기준을 반영해 별도 설계한다.
- [ ] UX 범위는 로그인, 대시보드, 포트폴리오, 상세, 검색, 히스토리, 관심종목, 설정 화면을 포함한다.
- [ ] 추가 개발 범위에는 월/연도 통계와 관심종목이 포함된다.

### 1-2. 핵심 기능

- [ ] Google 로그인
- [ ] 종목 검색
- [ ] Lot 등록
- [ ] Lot별 현재가 조회
- [ ] Lot별 수익률 계산
- [ ] 매도 전략 생성
- [ ] Lot에 전략 적용
- [ ] PositionRule 복사 저장
- [ ] 부분 매도 처리
- [ ] 잔여 수량 추적
- [ ] 매도 히스토리 저장
- [ ] 대시보드 기본 정보 표시
- [ ] 관심종목 관리
- [ ] 월별/연도별 통계 기초

## 2. DB 설계 필수 확인사항

DB 설계 시 AI는 최소한 아래 테이블과 관계를 검토해야 한다.

### 2-1. 필수 테이블 후보

- [ ] `users`: Google 로그인 사용자 정보
- [ ] `stocks`: 종목 마스터 또는 캐시 정보
- [ ] `lots`: 매수 묶음 핵심 테이블
- [ ] `strategies`: 사용자 매도 전략 템플릿
- [ ] `strategy_rules`: 전략 템플릿의 목표 수익률/매도 비율 규칙
- [ ] `position_rules`: 특정 Lot에 복사 저장된 실제 적용 규칙
- [ ] `sell_histories`: 실제 매도 기록
- [ ] `watchlists`: 관심종목
- [ ] `price_snapshots` 또는 가격 캐시 테이블 필요 여부 검토
- [ ] `exchange_rates` 또는 환율 캐시 테이블 필요 여부 검토

### 2-2. 사용자 분리

- [ ] 사용자별 데이터는 반드시 `user_id`로 분리한다.
- [ ] 다른 사용자의 Lot, 전략, 관심종목, 매도 기록에 접근할 수 없도록 설계한다.
- [ ] DB 레벨 제약 또는 애플리케이션 레벨 검증 중 어떤 방식으로 보호할지 명시한다.

### 2-3. Lot 설계

- [ ] Lot은 종목, 시장, 통화, 매수가, 매수 수량, 잔여 수량, 매수일을 저장한다.
- [ ] 같은 종목의 추가 매수도 별도 Lot으로 저장한다.
- [ ] 부분 매도 후 `remaining_quantity` 또는 동일 의미의 잔여 수량이 감소해야 한다.
- [ ] 매수 수량보다 많은 매도가 불가능하도록 제약을 둔다.
- [ ] 수량과 금액은 정수형이 아니라 소수 처리가 가능한 타입을 사용한다.
- [ ] KRW/USD 등 통화 구분을 명확히 저장한다.

### 2-4. Strategy / StrategyRule / PositionRule 설계

- [ ] `Strategy`는 사용자 전략 템플릿이다.
- [ ] `StrategyRule`은 Strategy에 속한 목표 수익률과 매도 비율 규칙이다.
- [ ] Lot에 Strategy를 적용할 때 `StrategyRule`을 직접 참조하지 않는다.
- [ ] StrategyRule 내용을 `PositionRule`로 복사 저장한다.
- [ ] Strategy 수정/삭제가 기존 Lot의 PositionRule에 영향을 주지 않는다.
- [ ] PositionRule은 `target_profit_rate`, `sell_ratio`, `is_executed`, `executed_at`을 포함한다.
- [ ] 이미 실행된 PositionRule은 중복 실행되지 않도록 한다.
- [ ] PositionRule의 실행 순서를 저장할 필요가 있는지 검토한다.

### 2-5. SellHistory 설계

- [ ] 매도 기록은 반드시 특정 Lot과 연결된다.
- [ ] 매도 가격, 매도 수량, 매도일, 트리거 수익률, 실현 수익을 저장한다.
- [ ] 어떤 PositionRule에 의해 실행된 매도인지 연결할 수 있는지 검토한다.
- [ ] 수동 매도와 전략 매도를 구분할 수 있는 필드가 필요한지 검토한다.

### 2-6. 관심종목 설계

- [ ] 관심종목은 사용자별로 저장한다.
- [ ] 종목 코드, 시장, 통화, 메모, 등록일을 저장할 수 있어야 한다.
- [ ] 관심종목은 Lot 등록 전 모니터링 용도로 사용할 수 있어야 한다.

### 2-7. 통계 설계

- [ ] 월별/연도별 실현 수익 계산이 가능해야 한다.
- [ ] 월별/연도별 매도 금액, 실현 수익, 수익률 계산 기준을 명확히 한다.
- [ ] 통계는 원화 기준으로 볼 수 있도록 환율 적용 기준을 검토한다.

## 3. 수익률 및 금액 계산 필수 확인사항

AI는 계산 로직 구현 시 아래 공식을 기준으로 검토해야 한다.

### 3-1. Lot별 수익률

- [ ] Lot 수익률은 `(현재가 - 매수가) / 매수가 * 100` 기준으로 계산한다.
- [ ] 수수료/세금 포함 여부를 명시한다.
- [ ] 통화가 USD인 경우 원화 환산이 필요한 위치를 명확히 한다.
- [ ] 현재가 조회 실패 시 기존 캐시 사용 또는 오류 표시 정책을 정한다.

### 3-2. 평가금액

- [ ] Lot 평가금액은 `현재가 * 잔여 수량` 기준이다.
- [ ] 전체 평가금액은 모든 보유 Lot 평가금액의 합계다.
- [ ] 미국 주식은 환율 적용 후 원화 합산 기준을 제공한다.

### 3-3. 실현/미실현 수익

- [ ] 실현 수익은 SellHistory 기준으로 계산한다.
- [ ] 미실현 수익은 현재 보유 중인 잔여 수량 기준으로 계산한다.
- [ ] 대시보드 총 수익은 실현 수익과 미실현 수익을 구분해서 표시한다.

### 3-4. 전체 수익률

- [ ] 총 투자원금 계산 기준을 명확히 한다.
- [ ] 총 평가금액 계산 기준을 명확히 한다.
- [ ] 총 회수금 계산 기준을 명확히 한다.
- [ ] 전체 수익률 공식은 구현 전에 명시하고 테스트한다.

## 4. 매도 전략 구현 필수 확인사항

### 4-1. 전략 생성

- [ ] 사용자는 여러 개의 Strategy를 만들 수 있다.
- [ ] Strategy는 하나 이상의 StrategyRule을 가질 수 있다.
- [ ] StrategyRule은 목표 수익률과 매도 비율을 포함한다.
- [ ] 매도 비율 합계가 100%를 초과하지 않도록 검증한다.
- [ ] 목표 수익률 순서가 중복되거나 충돌하지 않도록 검증한다.

### 4-2. Lot에 전략 적용

- [ ] Lot에 Strategy 적용 시 StrategyRule을 PositionRule로 복사한다.
- [ ] 복사 시점의 목표 수익률과 매도 비율이 PositionRule에 저장된다.
- [ ] 이후 Strategy가 변경되어도 기존 Lot의 PositionRule은 변경되지 않는다.
- [ ] Lot별로 서로 다른 PositionRule을 가질 수 있다.

### 4-3. 전략 실행

- [ ] 현재 수익률이 PositionRule의 목표 수익률 이상인지 확인한다.
- [ ] `is_executed=false`인 PositionRule만 실행 대상이다.
- [ ] 매도 수량은 Lot의 초기 수량 또는 잔여 수량 중 어떤 기준인지 명확히 한다.
- [ ] 매도 후 Lot의 잔여 수량을 갱신한다.
- [ ] SellHistory를 생성한다.
- [ ] PositionRule을 실행 완료 처리한다.
- [ ] 같은 PositionRule이 중복 실행되지 않도록 트랜잭션 또는 락을 검토한다.

## 5. API 설계 필수 확인사항

### 5-1. 인증 API

- [ ] Google 소셜 로그인 흐름을 정의한다.
- [ ] 로그인 후 사용자 식별자가 내부 `users` 테이블과 연결되는지 확인한다.
- [ ] 인증되지 않은 사용자는 보호 API에 접근할 수 없어야 한다.

### 5-2. 주식 API 연동

- [ ] 한국 주식과 미국 주식의 API 호출 방식을 구분한다.
- [ ] 종목 검색 API와 현재가 조회 API를 구분한다.
- [ ] 외부 API 장애 시 오류 처리 방식을 정의한다.
- [ ] API 호출 제한을 고려해 캐시 전략을 검토한다.

### 5-3. 환율 API 연동

- [ ] ExchangeRate-API를 사용한다.
- [ ] USD/KRW 환율 조회를 지원한다.
- [ ] 환율 조회 실패 시 정책을 정의한다.
- [ ] 환율 캐시 주기를 정의한다.

### 5-4. 내부 API

- [ ] Lot 생성/조회/수정/삭제 API
- [ ] Strategy 생성/조회/수정/삭제 API
- [ ] Lot에 Strategy 적용 API
- [ ] PositionRule 조회 API
- [ ] 부분 매도 API
- [ ] SellHistory 조회 API
- [ ] Dashboard summary API
- [ ] Watchlist 생성/조회/삭제 API
- [ ] 월/연도 통계 API

## 8. 보안 및 데이터 보호 필수 확인사항

- [ ] 모든 사용자 데이터 조회에는 사용자 식별 조건이 포함된다.
- [ ] 다른 사용자의 Lot, Strategy, SellHistory, Watchlist에 접근할 수 없다.
- [ ] Google 로그인 토큰 검증 흐름을 명확히 한다.
- [ ] API 키는 코드에 하드코딩하지 않는다.
- [ ] 환경 변수 또는 서버 설정으로 비밀값을 관리한다.
- [ ] 외부 API 오류 메시지에 민감 정보가 노출되지 않도록 한다.
- [ ] 금액/수량 변경 API는 입력값 검증을 수행한다.
- [ ] 삭제 기능은 실제 삭제와 소프트 삭제 중 정책을 명확히 한다.

## 11. 절대 놓치면 안 되는 핵심 규칙

- [ ] 평균단가 중심으로 설계하지 않는다.
- [ ] 추가 매수는 기존 Lot에 합치지 않는다.
- [ ] Lot은 독립 수익률과 독립 매도 전략을 가진다.
- [ ] StrategyRule은 Lot에서 직접 참조하지 않는다.
- [ ] Lot 적용 시 PositionRule 복사본을 만든다.
- [ ] Strategy 변경은 기존 Lot에 영향을 주지 않는다.
- [ ] 부분 매도 후 잔여 수량과 SellHistory를 반드시 갱신한다.
- [ ] 실현 수익과 미실현 수익은 반드시 분리한다.
- [ ] 한국/미국 주식과 환율을 고려한다.
- [ ] 사용자별 데이터 분리를 모든 API와 쿼리에서 보장한다.
- [ ] 테스트 없이 기능 완료로 판단하지 않는다.
